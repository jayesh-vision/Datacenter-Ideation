## 2. What the product is (scope and principles)

DCO is one application on top of the user's existing platform (VisionWaves / Databyte). It covers the datacenter
lifecycle in three menu groups plus admin:

- **Operate**: Command center, Revenue impact, Datacenters (site page with 3D twin), Facilities, AI & GPU, Alerts, Incidents, Change management.
- **Plan & Build**: Planner, Capacity, IP & Network (IPAM), DCIM, Delivery (programmes, projects), Work orders (BPMN processes).
- **Admin**: Compliance, Customization. **Reference**: Data model.

Scope rules the user set (keep them):
1. **Mock data only.** No production DB, backend APIs, collectors, auth or final data model. Everything is deterministic mock logic.
2. **Don't invent major capabilities** outside the requirements blueprint (`Data_Center_Operations_Master_Requirements_Blueprint_v0.1.docx`, ids DC-INV-*, DC-SITE-*, DC-NET-*, DC-FAC-*, DC-OPS-*, DC-CAP-*, DC-AI-*, WF-01…07). Gap fillers stay minimal and isolated.
3. **AI is deterministic mock logic** grounded in the data ("Opstral AI" copilot drawer, RCA hypotheses, recommendations). The planner's AI assist is deliberately **not** shown (user: the planner "looked generated by AI").
4. **Data must reconcile everywhere.** Every count is derived from entities, never typed in; screens that show the same figure must agree (QA scripts check this).
5. **Platform split, not ours to build:** identity and permissions (the platform), ITSM incidents and tickets (ServiceNow, visualised only), integrations and collectors (Databyte connectors; Redfish, SNMP, IPMI, Modbus agents), purchasing (ERP), catalogue, stock, warehouses and logistics (the user's supply chain platform).
   **Exception:** change requests are owned by DCO's own Change management module (DCO is the CR master; every change goes through a DCO CR).
6. **UI ideation first.** Backend and integration work only after the UI is mature. Mobile is low priority.
7. **Demo data must be complete:** a few fully populated exemplar records covering every variation beat thousands of sparse ones.

The operational story to preserve: Estate → Datacenter → Infrastructure → Connectivity → Services → Customers →
Events → Impact → Diagnosis → Recommended action.

## 4. Architecture

```
screens/*  ──imports only──▶  api/index.ts (async getX(), mutations, useQuery)  ──▶  mock/server.ts (queries, roll-ups, mutations)
                                     ▲ contract: api/types.ts                         │
                                                                                      ├─ mock/seed.ts + generate.ts (deterministic estate per persona × geo)
                                                                                      ├─ read models derived per data version (never change generated data):
                                                                                      │   physical, safety, access, lifecycle, vintage, maintenance, ops, revenue,
                                                                                      │   gpu-view, dcim, ipam, capacity, changemgmt, compliance, customization
                                                                                      ├─ delivery.ts + delivery-templates.ts + workflow.ts (build side)
                                                                                      └─ mock/p2b/* (planner record store, see below)
```

- `src/api/types.ts` is the API contract; `src/api/index.ts` is the **only** module screens import for data. Each function notes its future REST path, so going live = swapping bodies for `fetch`.
- `src/mock/` holds the generator, mock server and read models. **Screens never import `mock/`.**
- Shell `src/shell/` (Layout rail + top bar with persona and geography switches, ⌘K palette, Opstral AI drawer, embed mode). Pages call `usePage(crumbs, ctx)`.
- Shared UI `src/ui/` (`kit.tsx`: Chip, Btn, Panel, Kpi, Tabs, Seg, Drawer, Modal, Menu, KV, Empty, Info; `DataTable.tsx`; `ListToolbar.tsx`; `Analytics.tsx` StatGrid / StatTile; `status.tsx`), charts `src/charts/*`, vocabulary `src/lib/vocab.ts`.
- **Determinism:** every entity is seeded on its own id (`rngOf`), new random draws are appended after existing ones, so adding data never reshuffles the rest. `npx tsx .qa/fingerprint.ts <persona>` proves which collections moved.

**Planner sub-architecture** (ported from a colleague's prototype "P2B", rebuilt in our UI):
- Engine `src/planner/lib/*`: template inheritance, effective parameters with sources, sizing, cost / NPV / IRR, schedule from lead-time benchmarks, rule checks, readiness (`engine.ts`), wizard model (`wizardModel.ts`, `dimensions.ts`), governance (`governance.ts`: approval path by template and CapEx band, decisions, conditions, delegations, revisions, baseline), six plan families (`scopes/*`), sourcing (`sourcing.ts`), materials overrides (`materials.ts`), outputs and BOM (`outputs.ts`, `packModel.ts`), execute / closeout, reviews.
- Types `src/planner/p2b/types.ts`. Record store = P2B's MockDB (`src/mock/p2b/store.ts`), built per data version in `mock/p2b/index.ts` from our estate (`adapter.ts`) plus P2B's seed (`mock/p2b/seed/*`: 59 templates, 230 benchmarks, 15 demo plans placed on our sites by position). Money in USD inside the planner; India converts at `USD_RATE` 50.
- `src/planner/compat/*` connects the engine to our app without import cycles: registry, db proxy, `query.ts` (re-runs mounted queries on any planner or Delivery change), notify, people (two holders per approving role), clock, auth (switchable signed-in user), `delivery/handoff.ts`.
- `mock/p2b/bridge.ts` exposes approved / executing plans to Delivery.

## 5. Lifecycle chain: plan → build → operate

1. **Plan** (Planner): Draft → In review (approval path by template + CapEx band; segregation of duties) → Approved (baseline frozen) → Executing → Completed. Also Rejected, On hold, Cancelled; revisions B, C… supersede the parent once approved.
2. **Start the build** (`planner/lib/execute.ts`): hands the plan to Delivery and records the sourced BOM with its vendor orders, stock and rack holds, IP reservations and the plan type's records. Capacity → Reservations shows the holds.
3. **Delivery is the source of truth for the build.** Project `PRJ-n` = plan `PLN-n`: milestones from the plan's schedule, work orders = field work split into crew windows (own technicians or contractors), **one change request per work order**, POs = the plan's vendor orders (ordered at approval), commissioning L1 → L5, permits, design documents, EV cost, health.
4. **Work orders** run as BPMN process P10 instances (other processes: P01 site onboarding … P12 access request); completing steps moves the delivery work order.
5. **Handover** in Delivery (all work orders done + L5 passed) completes the plan and its capacity holds turn into live capacity.
6. **Operate**: the estate (DCIM, IPAM, Capacity, Facilities, twin) reflects what was built; DCIM edits themselves run under CRs.

Decisions behind the chain: every change is done through a DCO CR (standard = pre-approved templates, normal = approval matrix, emergency = fast path + review); processes run at project level (a programme is driven by its blueprint template); materials are advisory, never blocking (ERP owns POs, the supply chain platform owns stock and logistics).

## 6. The Planner in more detail (the most active area)

- **Hub** `/planning` (`Planner.tsx`): analytics strip, tabs Overview · Plans · Templates · Benchmarks & rules. Overview = IT power by plan type, Plans that need action (decisions, reviews, hard fails, late orders, conditions), Recently updated.
- **Wizard** `/planning/new`, `/planning/plans/:id/edit` (`PlanWizard.tsx` + `wizard/*`): plan type cards (accordion of groups, details panel) → Requirements (where, how much, needed-by with lead-time check; the planner fills inputs with reasons) → one step per design area (inputs with source and reset, result panels, drawings on Space / Power / Network, checks) → Scenarios → Review (blockers with fix links, approval path, outputs). Stage stepper (Set up · Design · Delivery · Business · Decide), live estimate rail, sticky action bar.
  Input fields (`wizard/ParamInput.tsx` `ParamFields`, 16-Oct-2026): aligned per row, hint text behind an ⓘ tooltip, source as dot + word, small reset icon only when a value differs.
- **Plan families** (`screens/planning/scopes/<family>`, registered via `registerScopeUi` / `uiFor`): in-site (rack, pod, hall, retrofit), plant (UPS, chillers), network (DCI paths and circuits), build (new datacenter, expansion, edge rollout, portfolio), replace (server / leaf refresh, rack replacement), migration (decommission). Each can add wizard panels, a site picker, requirements, pack sections and plan-page tabs.
- **Plan page** `/planning/plans/:id` (`PlanPage.tsx`, `plan/*`): header (title, status / Rev chips, facts, primary action, Send for review, **What-if** button for scenarios, Actions) → one status line → hero strip (readiness ring or % built; IT capacity · CapEx · Payback · Needed by · Rule checks) → **all tabs in one row**: Overview · Project plan · family tabs (Equipment, Inventory, Waves, Plant, Paths, Site fit) · Design (Sizing + Capacity) · Cost · Materials · Risks & permits · Rules · Approvals · Plan pack · Delivery · History. Old `?tab=capacity|baseline|scenarios` still work.
- **One edit rule** for every plan-page editor (`plan/edit/policy.ts` `usePlanEdit`): Draft / Rejected = save in place; In review = "Withdraw and save"; Approved / Executing = "Draft revision B" (the baseline stays frozen until B is approved); On hold / Completed / Cancelled = read-only with the reason. Risks and permits status updates are a live register on approved plans.
- **Editors**: Project plan (phases, dates, live effect on orders, CapEx, capacity), Materials (quantity, model swap, source, vendor or channel, add / remove lines; `plan.materialOverrides` flow through the engine, schedule, pack, review pack and Delivery POs), Equipment (replace / migration / in-site selections and waves), Risks & permits.
- **Plan pack** tab: what the plan creates, outputs, basis of design, BOM with sourcing, IP plan, drawings (generic + family sheets), build initiation, CSV exports, and the **Review pack**.
- **Review pack** (`pack/review/*`): one content model `ReviewDoc` built once (`buildReviewDoc`) and rendered as a vector PDF (pdfmake, Inter fonts), an Excel workbook (exceljs), a ZIP (fflate: PDF, workbook, CSVs, SVG drawings, README, manifest with SHA-256), and the **review portal** `/planning/plans/:id/review` (numbered sections, comments per section, decision panel bound to the approval flow, Send for review with an email preview; no real email is sent). Libraries are lazy-loaded.

## 7. Data: personas, geography, invariants

- **Personas** change vocabulary, customers, services and rack contents over the same sites: telco (routers, DWDM, operator servers), colocation (tenant cages, meet-me room), cloud / enterprise (leaf–spine + servers, storage, GPU hosts), NeoCloud (GPU clusters, InfiniBand + Ethernet fabrics, DCGM telemetry).
- **Geography** relabels the same 24 sites by position: India ids like `MH-DC-001` (hero site), USA `VA-DC-001` Ashburn (hero), `IL-DC-009` Chicago (UPS story), `CA-DC-020` (GPU fault). Never hard-code a site id in screens: use `dcAt(n)` in the generator and `defaultDcId()` in screens.
- **Money**: constants in rupees wrapped with `money()`, formatted with `fmtMoney()` / `fmtNum()` (never a literal ₹ or `toLocaleString('en-IN')`). Planner money is USD → geography via `common.tsx` `money()`.
- **Seeded stories** (keep them working): hero incident INC-0001 (backhaul flapping on the border router after the "Re-patch ODF" change CHG-2001), UPS-2 on battery with feed A lost at the UPS site, GPU Xid 79 stall on the biggest training job, NVLink straggler, CDU flow low, and others listed in CLAUDE.md.
- **Invariants guarded by scripts**, e.g. network persona India MH-DC-001 = 229 NE / 153 discovered / 21 drifted / 76 not discovered; revenue Σ issues = Σ causes = Σ datacenters = total; DCIM U and power sums; IPAM no overlaps.
- **Vintage** (`mock/vintage.ts`): 15–30% of servers and 10–20% of switches are the previous generation, with purchase dates, warranties, old or damaged racks, so refresh plans find equipment.

## 8. UI conventions (non-negotiable)

- **Design system: NST / Vision Waves.** Colours only via tokens (`--vw-color-*`, `--primaryColor*`); `.nst-table`, `.nst-btn`, `.vw-chip`; Poppins for chrome, Inter tabular for numbers. Source in `app/design-system/` and `src/styles/`.
- **Patterns**: `PageHead` → `StatGrid` of 6 `StatTile`s (list pages) → `Tabs` → `Panel` (with `info`) → `ListToolbar` + `DataTable`. Record pages: one header, one status line, a summary strip, tabs on one row. Drawers for details, modals for decisions.
- **Calm palette**: slate and white, brand blue accent; red / amber only for faults. No pastel tile walls, no gradients, no rows of boxed KPI tiles on landing pages.
- **No AI-looking chrome**: no coloured source badges on every number, uppercase micro-labels, confidence percentages, radar charts or "AI insight" cards. Sources show as quiet text with a tooltip.
- **Every widget gets an "i"** (`Info` in `ui/kit.tsx`): 1–2 sentences on what it shows, how it is computed, what clicking does.
- **Sentence case**, plain words, units on numbers, no NaN / undefined, no horizontal overflow at 1280 and 1440, side-by-side cards equal height, text never clipped.
- **All tabs visible** (no "More" menu where avoidable); keep tab labels short; tab counts only for things needing attention.
- **Planner CSS is global**: never reuse a class name another stylesheet already styles. `.pn-params`, `.pn-figs` and `.pn-hero` clashes broke the wizard three times; wizard classes are now `pw-*`, plan-page editors `peq-*`, materials `pm-*`.
- **Frozen**: the schematic digital twin `src/screens/site/twin/*` is signed off; don't edit it or run `twin.mjs` / `twin-full.mjs`.
