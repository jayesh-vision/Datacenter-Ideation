Core idea

The business model decides the data, not the building. Every datacenter shares one physical layer, and the current app already handles it for any operator. Four things change on top of it:

  • What sits in the racks: network gear, servers, or customer-owned equipment
  • Who the customer is: circuit buyer, tenant, cloud account, internal business unit
  • What a service is: L3VPN, cabinet lease, VM, business application
  • How a fault becomes impact: link → service, power circuit → tenant, host → instances

Mixed sites

Real sites are often mixed. A telco DC frequently has a colocation floor (Airtel's Nxtra and Jio do this), and a colocation provider may run its own cloud in one hall.

  • Profile per datacenter: sets the default vocabulary, KPIs and tabs.
  • Owner per rack: operator-owned or tenant-owned, so one site can hold both.
  • Optional profile per hall: only if a site runs two business models at scale.

Recommended rollout

  1. Now, small: add servers to the network DCs. OSS/BSS, NFV, DNS/AAA and CDN cache servers exist in real telco DCs. Model them as a separate asset class, so the agreed MH-DC-001 figures (179 / 103 / 21 / 76) still reconcile.
  2. Next: add Colocation as the second profile. It is the most common commercial model in India and the most different from today: tenants, contracted power, cross-connects and opaque customer gear. Convert 2–3 sites.
  3. Then: Cloud. Built around servers, capacity pools and instance impact. Enterprise is optional, because it overlaps heavily with Cloud.

Decisions needed before building

Which profiles to support?Suggestion: Network + Colocation first, Cloud later.
